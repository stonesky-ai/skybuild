# SkyBuild agent instructions

## Start and scope

- Work in the SkyBuild checkout. Before any Git or GitHub write, confirm `git rev-parse --show-toplevel` is that checkout and both `origin` fetch and push URLs point to `stonesky-ai/skybuild`. SkyKeep is a separate repository. Pass the checkout path explicitly to workflow scripts.
- Read the working contract at the start of [architecture.md](docs/design/architecture.md), under “Working contract for bounded assignments,” and the relevant architecture sections before planning or implementation. Read the full architecture for an architecture-wide review. Architecture governs [implementation_plan.md](docs/design/implementation_plan.md); update both in one revision when sequencing, interfaces, acceptance, or scope changes. Record open choices. Keep implementation briefs bounded and identify source revisions; summaries do not replace requirements.
- Read [ADR index](docs/adr/README.md) for decisions. Acceptance approves design, not implementation or deployment. Keep plans high level until implementation is ready. Split plans by area only when useful.
- Use normal prose in code, documents, commits, and other persisted output, even when chat is terse.

## Efficient tools

- Load [token-efficient coding](.claude/skills/skybuild-token-efficient-coding/SKILL.md) and available RTK and CodeGraph skills at session start. Load Serena's initial instructions when available; activate this exact checkout before a Serena symbol query or edit.
- When reusing another checkout's Python interpreter, set the task checkout's absolute `src` as `PYTHONPATH` and verify the imported package path before accepting test evidence. Provision with the project interpreter and require prerequisite success before dependent service starts.
- Verify `codegraph status /absolute/path/to/checkout` names this checkout before querying. Use the installed CodeGraph command-line CLI, not the MCP server. `status` takes the project path as a positional argument; `explore`, `query`, `context`, and `node` take `--path /absolute/path/to/checkout`. Do not pass `--project`; the CLI does not support it. If no local index exists, `codegraph init --yes` is authorized; keep the index local, Git-ignored, and limited to code. Sync after large pulls, branch switches, or merges. Use CodeGraph first for code navigation and impact; confirm absence claims independently. Use Serena for precise symbol work when useful and RTK for shell output. Avoid duplicate full reads.
- Use the matching project skill and guarded script for disposable PostgreSQL tests, reviewed PR integration, branch closeout, PR text, and CodeGraph checkout setup. Skills live in `.claude/skills/`; triggers also live in `.agents/skills/`. Skills do not grant new authority.
- During sustained coding, load [session failure review](.claude/skills/skybuild-session-failures/SKILL.md), run its ripgrep-backed scan every 30 minutes, inspect actual failures, and add a narrow prevention skill plus `.agents` trigger when a demonstrated repeat warrants it.
- For local preview start/stop controls shared across checkouts, follow [local process controls](.claude/skills/skybuild-local-process-controls/SKILL.md), including durable launch intent and atomic identity publication.
- During sustained work on each SkyBuild box, use [host watch](.claude/skills/skybuild-host-watch/SKILL.md) for one CPU-only minute-spaced status file. Check it before heavy gates; maintain the owner's 8 GiB memory reserve on this machine without model polling or broad process cleanup. The owner-directed disposable PostgreSQL gate uses its explicit 6 GiB admission floor.

## Authority and data

- Keep SkyBuild build tooling and its database separate from SkyKeep product code and data. Do not use or migrate SkyKeep's application database.
- The validated API cutover is complete. The authenticated SkyBuild REST API is the sole task authority for project `skybuild`; `docs/design/mastertodo.md`, `deferred.md`, and `alreadydone.md` are retired notices. Do not port ledger edits from older task branches or restore a ledger writer. Preserve stable task IDs and history through the API workflow. Repository review or integration does not authorize task completion attestations, fleet work, migration, or deployment.
- For the pre-MVP manual pilot, use REST/Cord to relay pinned assignments and results; the task API remains task authority. Verify private access and scoped worker credentials before dispatch. Follow [manual worker pilot](docs/design/implementation/manual_worker_pilot.md); do not infer automatic worker or model-launch authority from a message.
- Use **task** for the work unit and `/tasks` and `task_id` in new APIs. Preserve legacy IDs, filenames, and history where compatibility requires them. Keep attempts, processes, and bundles distinct from task identity.
- Give each unfinished task a phase, next action or named blocker, and owner. Follow [task_workflow.md](docs/design/task_workflow.md). Preserve immutable identity and lineage through scope, dependency, rework, split, merge, and deferral changes; invalidate affected evidence. Append journal corrections as new events. Keep basic task management and stuck-task visibility in core scope; defer multi-person approvals.

## Inference and long tasks

- Use existing subscription allowances and approved model/rate profiles for frontier inference. Switching account, engine, or host does not permit API billing, purchased-credit overage, or automatic top-ups. Qualify enforceable billing protection before unattended use; park inference when protection is unknown. Time or usage-percentage approval does not override this rule.
- Treat the friend's owner-confirmed zero-charge endpoint as a separate profile pending live qualification: reported Qwen 4, Recall 2, and BGE-M3 1 slots. Share its capacity across projects and tests, account for integration demand, and keep frontier review/fallback within actual allowances. Only small capability-discovery calls with the existing credential reference are authorized; do not reload models, stress test, or change infrastructure. Never expose credentials. Use ignored root `.env` variables `SKYBUILD_INFERENCE_BASE_URL` and `SKYBUILD_INFERENCE_SECRET_FILE` (a path to the token file), generic runtime names, and shareable `.env.example`. This scaffold authorizes neither an adapter nor a service start.
- Give every long-running task an appropriate automatic compaction threshold or verified checkpoint/restart policy. Let CPU observe processes; never poll an LLM with repeated large context. Preserve exact sources, effects, authority, and usage across restarts; a restart cannot duplicate work or renew approval.
- At approval expiry, checkpoint context, commit task-owned work, and attach a durable resume summary with barriers and useful owner questions. Closeout grace defaults to five configurable minutes; then stop all model queries, including nested calls. Grace does not extend implementation authority. Independently authorized CPU tasks retain their own lifecycle and report results without model watching. Preserve failed closeout evidence and persisted questions/answers; an answer does not renew approval.

## Review, integration, and Git

- Treat the launch-free API as a milestone before the self-building, parallel-worker MVP. Defer dedicated complexity/size gates and GUI until after MVP (`SKYBUILD-QUALITY-GATES`). Then prioritize pinned Ruff/McCabe checks and actual debt fixes. Start a serialized whole-repository review after 1,000 accepted commits or 5,000 changed source lines, whichever comes first. Wait for accepted published fixes for actionable findings; allow only explicit disposition of verified non-debt. Deduplicate runs/findings and expose thresholds in the GUI later. Follow architecture section 13 and [ADR 0034](docs/adr/quality.md#adr-0034).
- Run applicable project checks and independent adversarial review in a separate qualified model session for every code task before integration. Require actionable findings and independent re-review after fixes. Preserve task history and budgets. Authors cannot approve or weaken their own gates; wait when no reviewer is eligible. Follow [review_policy.md](docs/design/review_policy.md).
- Keep a separate descriptive branch, stable task ID, applicable checks and independent exact-head review for each code task. Push the task branch, but do not open an individual task PR or merge it directly to `dev-NNN`.
- Before bundle preparation, require a clear host-watch sample and reserve two worktree slots below its 64-worktree limit for the retained prepared candidate and the disposable integration candidate. If count exceeds 62, remove only clean worktrees owned by this session or its finished subtasks, after verifying all commits are pushed or otherwise preserved. Keep branches and evidence. Never remove dirty, locked, unknown-owner, or another session's worktree. If headroom cannot be established safely, defer bundle preparation and record the blocker.
- Integrate reviewed branches through one PR per frozen bundle into `dev-NNN`. At freeze, include every task ready for integration, in dependency order, up to the hard cap of 20 unique task IDs; do not send a one-task bundle while another ready task can fit. Admit urgent ready work at the next available opportunity; coalesce routine ready work for at most five minutes. Arrivals after freeze wait for the next bundle. Freeze heads, base, policy and membership; run one required full combined gate, publish only the passed candidate and confirm every task's inclusion. Reuse checks only with equivalent inputs, environment and trusted evidence. No extra owner merge prompt is required within existing authority. Runtime promotion retains its controls.
- Use sequential `dev-NNN` branches. Keep one standing dev-to-`main` PR after the branch has content; run its required full gate at cycle closeout, not after every bundle. Near 500 dev-branch commits, close at a coherent boundary by invoking the `Close-PR` skill (`.claude/skills/close-pr/SKILL.md`). Comment on features and limitations before merge. Title the standing PR `dev-NNN → main: [summary]`; let GitHub assign PR numbers and do not add manual `PR-NNN` prefixes. Preserve historical PR titles. Apply only documented SkyBuild procedures.
- Push owned source, docs, and committed handoffs to GitHub; record exact commit/branch and whether push is confirmed. Git pushes do not export database state. Use reset/clean only in task-owned worktrees. Clean branches/worktrees only after confirmed integration into the intended target; protect other workers and shared refs. Verify ownership and merge evidence. Do not impose a blanket destructive-Git ban. Follow [ADR 0026](docs/adr/integration.md#adr-0026).
- Plan daily PostgreSQL dump-file commits and separate low-priority restore/journal rebuild testing. Keep journal location and commit interval open. Never replay external effects or renew authority from restored state. GitLab and Bitbucket remain deferred.
