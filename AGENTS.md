# SkyBuild agent instructions

## Start and scope

- Work in the SkyBuild checkout. Before any Git or GitHub write, confirm `git rev-parse --show-toplevel` is that checkout and both `origin` fetch and push URLs point to `stonesky-ai/skybuild`. SkyKeep is a separate repository. Pass the checkout path explicitly to workflow scripts.
- Read the working contract and relevant sections of [architecture.md](docs/design/architecture.md) before planning or implementation. Read the full architecture for an architecture-wide review. Architecture governs [implementation_plan.md](docs/design/implementation_plan.md); update both in one revision when sequencing, interfaces, acceptance, or scope changes. Record open choices. Keep implementation briefs bounded and identify source revisions; summaries do not replace requirements.
- Read [ADR index](docs/adr/README.md) for decisions. Acceptance approves design, not implementation or deployment. Keep plans high level until implementation is ready. Split plans by area only when useful.
- Use normal prose in code, documents, commits, and other persisted output, even when chat is terse.

## Efficient tools

- Load [token-efficient coding](.claude/skills/skybuild-token-efficient-coding/SKILL.md) and available RTK and CodeGraph skills at session start. Load Serena's initial instructions when available; activate this exact checkout before a Serena symbol query or edit.
- Verify `codegraph status` names this checkout before querying. Use this session's CodeGraph MCP server with an explicit `projectPath`, or run CodeGraph locally here. Never reuse another session's server or checkout's index. If no local index exists, `codegraph init --yes` is authorized; keep the index local, Git-ignored, and limited to code. Sync after large pulls, branch switches, or merges. Use CodeGraph first for code navigation and impact; confirm absence claims independently. Use Serena for precise symbol work when useful and RTK for shell output. Avoid duplicate full reads.
- Use the matching project skill and guarded script for disposable PostgreSQL tests, reviewed PR integration, branch closeout, PR text, and CodeGraph checkout setup. Skills live in `.claude/skills/`; triggers also live in `.agents/skills/`. Skills do not grant new authority.

## Authority and data

- Keep SkyBuild build tooling and its database separate from SkyKeep product code and data. Do not use or migrate SkyKeep's application database.
- Until the documented API cutover, manage tasks only in `docs/design/mastertodo.md`, `deferred.md`, and `alreadydone.md`. Keep each stable task ID in exactly one ledger. Planning does not authorize live queue changes, fleet work, migration, or deployment.
- Use **task** for the work unit and `/tasks` and `task_id` in new APIs. Preserve legacy IDs, filenames, and history where compatibility requires them. Keep attempts, processes, and bundles distinct from task identity.
- Give each unfinished task a phase, next action or named blocker, and owner. Follow [task_workflow.md](docs/design/task_workflow.md). Preserve immutable identity and lineage through scope, dependency, rework, split, merge, and deferral changes; invalidate affected evidence. Append journal corrections as new events. Keep basic task management and stuck-task visibility in core scope; defer multi-person approvals.

## Inference and long tasks

- Use existing subscription allowances and approved model/rate profiles for frontier inference. Switching account, engine, or host does not permit API billing, purchased-credit overage, or automatic top-ups. Qualify enforceable billing protection before unattended use; park inference when protection is unknown. Time or usage-percentage approval does not override this rule.
- Treat the friend's owner-confirmed zero-charge endpoint as a separate profile pending live qualification: reported Qwen 4, Recall 2, and BGE-M3 1 slots. Share its capacity across projects and tests, account for integration demand, and keep frontier review/fallback within actual allowances. Only small capability-discovery calls with the existing credential reference are authorized; do not reload models, stress test, or change infrastructure. Never expose credentials. Use ignored root `.env` variables `SKYBUILD_INFERENCE_BASE_URL` and `SKYBUILD_INFERENCE_SECRET_FILE` (a path to the token file), generic runtime names, and shareable `.env.example`. This scaffold authorizes neither an adapter nor a service start.
- Give every long-running task an appropriate automatic compaction threshold or verified checkpoint/restart policy. Let CPU observe processes; never poll an LLM with repeated large context. Preserve exact sources, effects, authority, and usage across restarts; a restart cannot duplicate work or renew approval.
- At approval expiry, checkpoint context, commit task-owned work, and attach a durable resume summary with barriers and useful owner questions. Closeout grace defaults to five configurable minutes; then stop all model queries, including nested calls. Grace does not extend implementation authority. Independently authorized CPU tasks retain their own lifecycle and report results without model watching. Preserve failed closeout evidence and persisted questions/answers; an answer does not renew approval.

## Review, integration, and Git

- Treat the launch-free API as a milestone before the self-building, parallel-worker MVP. Defer dedicated complexity/size gates and GUI until after MVP (`SKYBUILD-QUALITY-GATES`). Then prioritize pinned Ruff/McCabe checks and actual debt fixes. Start a serialized whole-repository review after 1,000 accepted commits or 5,000 changed source lines, whichever comes first. Wait for accepted fixes or dispositions from the prior review, and deduplicate runs/findings. Expose thresholds in the GUI later. Follow architecture section 13 and ADR 0034.
- Run applicable project checks and independent adversarial review in a separate qualified model session for every code task before integration. Require actionable findings and independent re-review after fixes. Preserve task history and budgets. Authors cannot approve or weaken their own gates; wait when no reviewer is eligible. Follow [review_policy.md](docs/design/review_policy.md).
- Integrate reviewed tasks in fixed bundles after combined-candidate gates pass. Freeze heads, base, policy, and membership; queue arrivals for the next bundle. Verify published content and per-task inclusion before completion or cleanup. No extra owner merge prompt is required within existing authority. Runtime promotion retains its controls.
- Use sequential `dev-NNN` integration branches and descriptive change branches. After the first change-branch commit, push and open a sequential `PR-NNN` targeting the dev branch. Keep a dev-to-`main` PR once the dev branch has content. Near 500 dev-branch commits, close at a coherent boundary using SkyKeep's `close-pull-request` and `branch-pr-merge` skills; add a substantive PR comment covering features and limitations first. Apply SkyKeep-specific host, queue, or release steps only when SkyBuild has matching machinery.
- Push owned source, docs, and committed handoffs to GitHub; record exact commit/branch and whether push is confirmed. Git pushes do not export database state. Use reset/clean only in task-owned worktrees. Clean branches/worktrees only after confirmed integration into the intended target; protect other workers and shared refs. Verify ownership and merge evidence. Do not impose a blanket destructive-Git ban. Follow ADR 0026.
- Plan daily PostgreSQL dump-file commits and separate low-priority restore/journal rebuild testing. Keep journal location and commit interval open. Never replay external effects or renew authority from restored state. GitLab and Bitbucket remain deferred.
