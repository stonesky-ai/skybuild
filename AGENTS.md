# SkyBuild working instructions

## CodeGraph for every agent

Every author, reviewer and subagent must load the available CodeGraph skill and use CodeGraph for source-code orientation, symbol lookup, call paths and change impact whenever it can answer the question. Check `codegraph status` in the current checkout first and verify that its project path is that checkout. The owner authorizes `codegraph init --yes` when that checkout has no `.codegraph/` index; keep each checkout's index local and ignored by Git. Use the CodeGraph MCP server started by the agent's own session with an explicit `projectPath`. If that server is unavailable, run `codegraph` locally from the same checkout. Never reuse another agent's server or a different checkout's index. Run `codegraph sync` after a large pull, branch switch or merge before trusting graph results. Use direct source reads or search when CodeGraph cannot cover the question, and confirm zero-caller or other absence claims independently. Do not index credentials or non-code corpora.

At session start, load [the token-efficient coding skill](.claude/skills/skybuild-token-efficient-coding/SKILL.md), the available RTK and CodeGraph skills, and Serena's initial instructions when its tools are available. Use CodeGraph to narrow code context, Serena for precise symbol edits when useful, and RTK for shell output; avoid reading the same source twice. For repeatable gates and GitHub operations, select the matching project skill under `.claude/skills/` and run its guarded Python script. Skills do not grant authority to merge, delete branches, deploy or touch live databases.

Read [docs/design/architecture.md](docs/design/architecture.md) before planning or implementation, starting with its working contract and reading the sections relevant to the task. For an architecture-wide review, read the complete governing document. Use bounded source/context excerpts for implementation briefs and record their revision/hashes; summaries never override the relevant full requirements. [docs/design/implementation_plan.md](docs/design/implementation_plan.md) derives from it and must change in the same revision whenever an architecture change affects sequencing, interfaces, acceptance or scope. Do not resolve a disagreement by treating the implementation plan as authority. Record unresolved choices explicitly.

Read [docs/adr/README.md](docs/adr/README.md) for decision history. ADR acceptance records a design decision, not implementation completion or permission to deploy.

Until the documented API cutover, tasks live only in docs/design/mastertodo.md, deferred.md and alreadydone.md. Preserve stable task IDs when moving between files; keep each ID in exactly one ledger. Planning a task does not authorize running it. No live queue updates, fleet activity, migration or deployment are authorized by these documents.

This repository owns the build tooling extracted from SkyKeep. Product repositories retain their application code, product tests and project-specific build contracts. Preserve the separate SkyBuild database boundary. Do not use or migrate the SkyKeep application database.

The owner requires existing subscription allowances and approved model/rate profiles for frontier inference. Account/engine/host switching does not authorize API billing, purchased usage-credit overage or automatic top-ups. Qualify enforceable billing protection before unattended adoption; unknown protection parks inference. No usage-percentage or time approval overrides this restriction.

The friend's shared endpoint is a separate owner-confirmed zero-charge inference profile: reported Qwen 4, Recall 2 and BGE-M3 1 slots, pending live qualification. Respect distinct roles, a shared cross-project/test capacity ledger and integration demand. Subscription quota is not applicable to its own calls; frontier coordination/review/fallback still consumes actual allowance. The owner authorized small capability-discovery requests using the existing credential reference, not model reloads, stress tests or infrastructure changes. Never print or copy credentials into planning artifacts. Installation-specific discovery settings live in the ignored root `.env`: `SKYBUILD_INFERENCE_BASE_URL` and `SKYBUILD_INFERENCE_SECRET_FILE`. The latter contains a path to the external bearer-token file, not the token. Use generic configuration names and the shareable `.env.example`; do not hardcode an owner's endpoint or file path in runtime code. This configuration scaffold does not implement an adapter or authorize service starts.

Every long-running task needs an explicit appropriate automatic compaction threshold or a verified restart-me checkpoint/restart policy. CPU observers monitor external processes; do not send repeated large context to an LLM on timer ticks. Checkpoints preserve exact sources, stable tasks/effects, current authority and usage history. A reasoning-session restart cannot duplicate a running task, renew approval or reset budgets.

At task approval expiry, prepare a compact context checkpoint, task-owned WIP commit and durable task-linked resume summary with barriers and any owner question that could enable fast completion. Closeout grace defaults to five minutes, configurable in the control website, and ends in a hard cutoff of model queries, including nested calls; it grants no implementation extension or additional usage. Independently authorized CPU tasks continue within their own lifecycle and report durable results without model watching. Persist owner questions/answers through the task and control panel; an answer does not renew expired approval. Preserve incomplete closeout evidence on failure.

Assume every project pushes owned source/docs and committed handoff artifacts to GitHub. Record exact commit/branch and confirmed versus pending push; pushes do not preserve unexported database state. GitLab/Bitbucket support remains deferred. Daily PostgreSQL dump-file commits are planned as a scheduled CPU task; restore and journal-based rebuild testing is a separate proposed low-priority task. Journal location and commit interval remain open. Preserve the dedicated database boundary and never replay external work or renew authority merely by restoring state. Do not impose blanket prohibitions on destructive Git commands. Within authorized task scope, allow reset/clean in task-owned worktrees and branch/worktree cleanup after a confirmed PR merge into the intended target branch. Protect other workers’ work and shared branches; verify both worktree/ref ownership and actual merge evidence. The accepted policy in ADR 0026 does not require another prompt merely because the command is destructive.

Use task as the canonical work term. Preserve exact legacy identifiers, ledger filenames and stable IDs where compatibility/history requires them; use `/tasks` and `task_id` in the new API. Attempts/processes and bundles describe execution/grouping rather than duplicate work queues.

Every unfinished task needs an explicit workflow phase, next action or named blocker, and responsible component/person. Follow the architecture-derived docs/design/task_workflow.md flowchart and transition contract. Task scope, definition of done, dependencies, rework, split/merge and deferral actions preserve immutable identity/lineage and invalidate affected evidence. The task journal is append-only: corrections add events; neither an ADR nor a runtime endpoint may rewrite or delete historical entries. Basic task management and stuck-task visibility are core; multi-person approval chains are explicitly deferred until much later.

The MVP is a running SkyBuild that rebuilds and extends itself with parallel workers under the existing controls. The launch-free API is an earlier milestone. Dedicated complexity/size gates, reports and their GUI are deferred until MVP is running, tracked as SKYBUILD-QUALITY-GATES; do not make them MVP prerequisites.

After MVP, prioritize pinned Ruff/McCabe code-review checks and cleanup of every actual finding they expose. Run a serialized whole-repository background review after the first of 1,000 accepted commits or 5,000 changed source-code lines. Do not start the next review before all actual debt findings from the prior review have accepted published fixes. Deduplicate accidental duplicate runs and findings; expose both thresholds in the GUI later. Follow architecture section 13 and ADR 0034 for the authority and counting boundaries.

Every code task requires existing applicable project checks followed by adversarial review in a separate qualified model session before integration. Findings must identify affected code/contracts and concrete fixes or tests; correction, retesting and independent re-review preserve the same task history and budgets. Follow architecture section 13 and docs/design/review_policy.md for retained post-MVP GUI-configurable complexity/size criteria and trusted policy boundaries. The author cannot self-approve or weaken its own gates; no eligible reviewer means waiting for review.

Automatically integrate ready reviewed tasks in fixed bundles after the combined candidate’s required gates pass. New tasks wait for the next bundle; no per-task full integration run or extra owner merge prompt is required by default. Verify exact heads/base/policy, publication and per-task inclusion before completion/cleanup. Runtime deployment/promotion keeps its existing controls. Core integration bundling is required earlier than deferred cloud batching.

Use a numbered development branch as the integration trunk, starting with `dev-001` and incrementing the number for each later cycle. Create a separate, descriptive branch for each change from the current development branch. After the first commit on a change branch, push it and open a sequentially numbered pull request (`PR-001`, `PR-002`, and so on) targeting the development branch. Keep a development-branch pull request targeting `main` once that branch has content. Track the development branch's commit count; near 500 commits, close the cycle at a coherent integration boundary using SkyKeep's `close-pull-request` and `branch-pr-merge` skills. Before merging that pull request, add a substantive comment summarizing the features and known limitations in the branch. Preserve the exact PR head, target, review and combined-gate evidence when integrating change branches. Do not apply SkyKeep-specific host, queue or release steps to SkyBuild without verifying that SkyBuild has the corresponding machinery.

Keep plans high level until an area is ready for implementation. Split an implementation plan by area only when it improves review or ownership; keep the parent sequence and architecture references current. Persisted documents, code and commits use normal English even when chat uses terse phrasing.
