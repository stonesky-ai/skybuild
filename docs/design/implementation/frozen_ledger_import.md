# Frozen SkyBuild ledger import rehearsal

This records an earlier disposable PostgreSQL rehearsal of SKYBUILD-TASK-CUTOVER. That rehearsal did not switch task authority: its receipt deliberately recorded `authority = markdown`, and Store refused API task writes for the rehearsed project. The later live cutover is complete. As of 2026-10-10, the authenticated SkyBuild API is the sole task authority; `mastertodo.md`, `deferred.md` and `alreadydone.md` contain retirement notices.

## Frozen inputs and mapping

The rehearsal source commit was `6d96075f88493d0b54577a2a8c9526f19a78a5ed`. The three source SHA-256 values and canonical manifest hash are in [frozen_ledger_import.json](frozen_ledger_import.json). The importer checks the input bytes against both that contract and the exact Git blobs at the pinned commit before touching a database. It requires a reviewed import-plan SHA-256 on apply; this digest covers every projected record and the explicit dependency arrays. The reviewed rehearsal plan digest was `1d3400fc5ae31ddfbc9e7e55e3b231b070cf7456e11921728aac6e074cdbcdc0`. The later live import used [current_task_import.json](current_task_import.json) at source commit `d79d2e1947d2c8e9edb577ab5f5093edfa3c94e3`, content digest `307019c967c0531912be0441809da8d89ca506905ff63594976bf5463ba142c7`, and import digest `b25770457bc3c55d5697e67cb582a302ed39712b2693c3218e0079517376663a`.

Every task ID has an explicit dependency array in the JSON contract. Edges name only stable SkyBuild task IDs that are unconditional prerequisites in the present planning record. Phrases such as “controlled execution,” “applicable slice,” “when selected,” “before broad enrollment,” and “later” remain in the raw brief; they are not silently converted into edges. The broad legacy migration is not a machine dependency of the disjoint SkyBuild self-build target. A later owner-reviewed mapping revision must produce a new plan digest.

The task description stores the complete original Markdown section, including status, full brief, deferral reason/revisit trigger, completion result/evidence, architecture reference and any other field. Metadata records source filename and hash, commit, manifest hash, raw-section hash, source order and original status text. Structured title, normalized status, priority order, acceptance text, architecture reference and explicit dependency IDs are projections for API queries. Where source prose has no unambiguous standalone phase, responsible person, assignee or blocker, the importer uses `phase = imported`, `responsible = owner`, `assignee = null`, `blocker = null`, and a manual review next action for unfinished tasks. These defaults do not assert that the ledger named those values. Field reconciliation was a prerequisite for the later authority switch; any remaining task-field corrections now belong in the API workflow. The raw section remains the lossless evidence.

## Rehearsal and acceptance boundary

The historical rehearsal used `python -m skybuild ledger-import` from the repository root to inspect the full dry-run plan without database access. Reproducing it requires the pinned source files in an isolated checkout; the current retirement notices are not import inputs. For an isolated database whose exact configured name starts with `skybuild_import_test`, explicitly run migrations and then use `ledger-import --apply-disposable --expected-import-sha256 <reviewed digest>`. Apply locks all application data tables for its emptiness check and transaction. It refuses an unrelated nonempty destination, changed ledger bytes, changed mapping, or an altered imported destination. Pre-provisioned principals and grants are allowed because they are authentication setup, not task data. Repeating the same import against unchanged rows returns `unchanged` without adding history.

The rehearsal imported 28 tasks: 5 in progress, 9 proposed, 12 deferred and 2 done. The CLI's separate-process replay returned `unchanged`. PostgreSQL tests cover dry-run fidelity, changed source and mapping refusal, unrelated destination refusal, transaction rollback on journal failure, API read/history and write denial, conflicting replay, and Store recreation after import. This rehearsal changed no live ledger files, authority manifest, deployment or worker process. The subsequent live cutover used a later pinned 38-task source and reviewed import digest, switched the project receipt to `api`, and preserved the imported task history. The current API serves 60 tasks after 22 later task creations; those later tasks were not part of this rehearsal or the frozen import.

After migration 004 added task lineage, replay verification was tightened to reject unexpected lineage rows, multiple import receipts and changed receipt task/status counts or authority. It locks the lineage table with the other application data tables. The importer now takes the receipt-table lock before task-table locks, matching the order in which task writers read authority and then mutate tasks. A paused-writer PostgreSQL regression confirms the importer waits for the writer to commit and then refuses the nonempty destination, without a lock-order deadlock. This remains a rehearsal verifier, not an authority switch.

Independent `import_review` accepted the replay and lock-order corrections. The focused importer suite passed 10 tests; the full disposable suite passed 144 with the existing Starlette warning.
