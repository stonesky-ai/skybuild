## Observed launch pattern and failure controls

- Installed `procs/history.log` records integrator starts at 03:41:48, 03:45:40, 03:49:19, and 03:51:11 UTC on October 8, followed by Codex starts at 15-minute intervals from 12:55 to 15:20 UTC. `logs/respawn-roles.log` records the latter as spawns with changing fingerprints and gaps near 900 seconds; 14:30 and 15:35 checks said `already running`. Those records prove repeated launch attempts, not token totals, completed model calls, or cause of each exit.
- Bounded `logs/integrator.log` metadata shows 15:20:28 UTC start and 15:48:35 UTC `done` after one tooling integration. Thus at least that run completed work. The registry JSON records its PID and launch, but is a last-launch record, not proof of a live process. Role output transcript was not read.
- One-process protection exists in `spawn_role.sh:11-13`; respawner also uses file lock, minimum gap, heartbeat, usage cutoff and max runtime. Keeper has usage, memory, disk, short-session backoff, row holds, tripwire, persistent STOP and DRAIN controls (`session_keeper.py:8-70`; `keeper_ensure.sh:8`). Fleet-watch has its own cooldown and session-presence check (`fleet_watch.py:133,1359`). These controls are local to each launcher; no single global Skymaker admission or stop gate is shown by these sources.
- Durable drain likely requires stopping all independent launchers and honoring keeper STOP/DRAIN and unit restart policies. This is architecture inference, not an instruction to operate services. `skykeep-todo-service.service` restarts automatically; `keeper_ensure.sh` starts an inactive keeper unless DRAIN exists. A paused `respawn_roles.sh` does not by itself pause fleet-watch or watchdog.

Exact thresholds, enabled roles/actions, box capacity, and live endpoints are unknown. The installed launcher itself pins a dev-016 branch; roles checkout is newer than the main checkout. Treat that status paragraph as stale until unit and API are checked.
