## 2. Product and extraction boundary

SkyBuild is Stonesky's build product, in the dedicated stonesky-ai/skybuild repository. Cord is its durable communications capability; Keeper is its worker supervisor. SkyKeep remains the vault application. SkyTrends remains the metrics product; SkyAudit and SkyHermes remain separate products. Dark Build Factory material is historical research.

**Owner-confirmed scope: extract all build tooling from SkyKeep into SkyBuild.** This includes reusable infrastructure and SkyKeep-specific orchestration currently mixed into that infrastructure. Project-specific knowledge becomes a versioned project adapter; it does not justify leaving a second build platform in SkyKeep.

| Family to extract | Included responsibility | Boundary retained by a product repository |
| --- | --- | --- |
| Work and persistence | REST API, Store, migrations/importers, shared clients, task views, claims, history, reviews, lessons and integration records. | Product work content and references to its source; no direct build-database writer. |
| Cord | Durable messages, delivery/handling records, replies and coordination clients. | Project-specific recipients and policies. |
| Execution | Keeper, engine/shell adapters, worktree lifecycle, checkpoint/drain/update, box enrollment and aragog lifecycle adapter. | Product build commands and required capabilities. |
| Supervision and admission | Role launchers, overseer/marshalls, dispatcher, integrator, reviewer, merge preparation, bundling, fleet-watch, watchdog and ensure paths. | Source/review/merge policy expressed through the adapter. |
| Integration and verification | Task scanners, readiness, leases, gates, remote runners, lane/resource orchestration and result collection. | Product tests, fixtures, lane definitions and verification requirements. |
| Observation and operations | Process/unit/box/usage collectors, session/result readers, status/console, diagnostic probes, log miner, bounded recovery and cleanup. | Application telemetry remains the application's responsibility. |
| Installation and developer tooling | Service units, timers, deployment/update scripts, generic skills and CLI commands, tooling documentation and tooling tests. | Thin compatibility commands during migration; product-specific skills and application deployment configuration. |

The extraction census must classify every entry point, caller, scheduled task, direct SQL writer, skill, test and installed artifact as move, project adapter, temporary compatibility wrapper, or retire. No component is considered extracted while an unaccounted launch path or writable copy remains. Preserve useful behavior before simplification. Keep mechanical moves distinct from persistence or lifecycle changes so failures remain attributable.

SkyKeep and SkyBuild are separate registered projects with immutable IDs from the beginning. Project identity is carried through tasks, messages, claims, runs, resources and authorization. Full simultaneous autonomous multi-project operation is later work; the complete extraction itself is required scope.

Owner-confirmed repository assumption: every project pushes source, documentation and committed task/handoff artifacts to its configured GitHub repository. Normal build delivery includes pushing the owned task branch; GitLab and Bitbucket support are deferred under SKYBUILD-GIT-HOSTS. Keep repository/base-branch/task-branch configuration small; no generic hosting framework is needed initially. Record the exact local commit and whether its remote push was confirmed. An offline/failed push remains pending and cannot be described as remotely preserved. A push does not merge a pull request, deploy a product or override task authority. GitHub pushes do not back up unexported PostgreSQL task/message state.

Owner-confirmed Git lifecycle: allow reset/clean inside task-owned worktrees and branch/worktree cleanup after a confirmed PR merge into the intended target/higher-level branch. Protect other workers’ work and shared branches. Build instructions and ADRs must not impose blanket destructive-command bans or require another prompt solely because an operation is destructive within this authorized scope. [ADR 0026](../adr/integration.md#adr-0026) records the accepted rule.

Proposed lifecycle checks verify the task-owned worktree and affected ref, not only the directory name; a worktree-local command can also move a branch ref. Confirm the actual PR target and merge outcome, accounting for squash/rebase and commits added after the merge. A closed-but-unmerged PR is not sufficient cleanup evidence, and new changes must not silently be treated as merged. Apply existing ownership/fencing to avoid cross-worker cleanup; keep these checks in the shared Git/worktree lifecycle rather than scattered command prohibitions.

### Manual pre-MVP worker relay

Before managed worker admission is qualified, use the SkyBuild REST/Cord service only as a manually dispatched assignment and result relay. PostgreSQL/API owns current task state; a Cord message carries a pinned brief, not execution or spending authority. Before dispatch, the client authenticates to the API and checks the task ID, revision and eligible workflow state; the current manual relay performs these checks while pinning the committed brief. It does not claim, reserve or lease the task, so the human dispatcher must prevent overlapping assignments. The dispatcher records a stable task ID, assignment ID, worker, exact base and brief hash, owned paths, checks and model limit before sending. A manually started worker returns its exact pushed branch/head, checks, changed paths, blockers and next action. REST dispatch, inbox waits, and result notifications are CPU/network work with no model-token cost by themselves. A CPU poller or bounded inbox wait may collect and batch results; no dispatcher response is needed until a worker is blocked on a decision, an ownership/deadline boundary is near, or a safety issue needs action. Route `in-progress` results to CPU record-only, `blocked` results to owner attention, and `ready-for-review` results through deterministic exact-head checks before independent review. Only the last class requires review; result arrival never launches a model by itself. Before a SkyBuild-managed model process starts, a preflight must read current task eligibility from the authenticated API and require an eligible task, exact source revision, hash-pinned inputs, substantive operation, concrete deliverables and acceptance criteria. This proves a work need only; provider, account, budget and approval controls remain separate. Duplicate messages keep one assignment identity; message expiry is not an ownership lease. Reconcile a missing worker's session, refs and last report before reassignment. No automatic worker daemon, second task queue or direct task-branch merge is part of this pilot. A separate qualified reviewer checks each exact head before bundle integration. Private reachability, scoped credentials and a durable send/receive/acknowledge round trip must be verified from each selected box first. This pilot can overlap implementation work but does not satisfy the controlled parallel-worker MVP by itself.

Owner directive, 2026-10-09: stage this bounded manual pilot with one local worker on jeltz, then two local workers on jeltz, then one remote worker on a qualified box. This is a narrow exception to jeltz's general build-worker allocation exclusion, not a change to automatic placement. Each stage retains per-worker resource and model limits, current task/assignment checks, independent review and the existing stop and billing controls. The directive does not assert that any worker is running or authorize a managed worker/model launcher.

Owner directive, 2026-10-10: exercise the README task with one bounded automatic CPU worker on Wonko, using REST/Cord to receive, claim, renew and submit actual work. Use the committed [Wonko smoke brief](assignments/wonko-rest-worker-smoke-20261010.json) to append exactly one `modified on` line and the actual execution datetime with an America/Chicago offset to the selected README. No person must perform the worker's edit as a prerequisite. Observe actual task construction, validation, exact-head independent review, frozen bundle, confirmed dev inclusion and REST acceptance, then close the dev cycle into main. Verify the accepted Petri runtime and the separately scoped worker credential before dispatch; source integration alone proves neither migration 013 nor runtime qualification. This authorizes one bounded CPU invocation, without inference or a worker daemon, and does not qualify automatic placement, model launching or the full concurrent-worker MVP. Reconcile existing tasks through the sole REST authority rather than reimporting retired ledgers.

### Automatic bundled integration

Owner-confirmed: automatically integrate independently reviewed task branches through one bundle PR into the configured integration branch after required tests pass, using bundles as the normal unit of integration. Task production can outpace hour-long integration tests; twenty completed implementations during a test run are an owner example, not a batch-size default or throughput promise. Tasks finish implementation and cheap affected checks independently, then wait for integration where the project’s acceptance requires it. Keep an implementation-ready task in progress, with a ready-for-integration/integrating phase, until its configured acceptance is met. This is a phase of the same task, not another work queue with duplicated task identities. No fresh owner merge prompt is required for an eligible bundle within existing authority. Runtime promotion/deployment retains its existing policy. [ADR 0028](../adr/integration.md#adr-0028) records the accepted direction.

Proposed compact pipeline: one fenced integrator per project/target collects ready tasks, orders dependencies, and freezes member task IDs/heads, target/base, gate/review policy and a combined candidate. Required task reviews and cheap checks bind to exact task heads; integration gates bind to that combined candidate and its relevant source/config/environment. Any integration-only edits require fresh review and a new candidate. Required gates are the union of project and member requirements, deduplicating equivalent checks; a profile replaces another only when explicit policy establishes that it covers every requirement. Profiles are not assumed to have a total order. Take gate/review policy from the accepted control configuration; a candidate cannot reduce its own checks. Tasks arriving during tests accumulate for the next bundle; do not mutate or restart the active candidate to include them. Prepare readiness for the next bundle while the current gate runs, and dispatch the next bounded bundle when its integration lane is free. Urgent ready work enters the next available integration opportunity. Routine ready work may wait at most five minutes for coalescing; this does not interrupt an active gate. Bundle count and size limits remain configuration choices.

After passing gates, publish the exact tested result through the project’s configured PR/branch flow and record the tested candidate, confirmed target commit and per-task membership, verifying the published content/base relationship rather than assuming equal commit hashes. Create one PR per frozen bundle, not one per task. Confirm each reviewed task head is included in the published target; a PR closure alone proves neither review nor task inclusion. A changed member head or target/base requires new candidate/evidence rather than stale acceptance. Unknown merge acknowledgment retains pending ownership until observed reconciliation; cleanup waits for confirmed integration. Shared-branch protection applies to destructive rewriting, while this authorized merge flow can advance the branch. No gate/protection bypass or self-reduction of required checks is permitted.

The standing `dev-NNN` to `main` PR remains open during the cycle. Run one full gate on each frozen bundle candidate, not on each task branch. Run the standing PR's required full gate at coherent closeout near 500 dev-branch commits, not after each bundle. Title new standing PRs `dev-NNN → main: [summary]` and use GitHub-assigned PR numbers without manual numeric title prefixes; historical PRs are unchanged. Reuse a prior check only when its inputs, environment and trusted evidence are demonstrably equivalent.

Publication needs enforcement at the external write, not just a database lease or a prior branch read. Proposed mechanics: keep one durable publication intent and unresolved publication slot per target; a trusted publisher validates current ownership and exact candidate, then uses a qualified GitHub PR flow that enforces the tested head/base relationship at merge time. GitHub's merge `sha` parameter guards the PR head, not an expected base; strict branch protection or an equivalently qualified flow must supply the missing protection. An accepted/enqueued request is not a confirmed merge. Retain the operation reference and reconcile actual target/task inclusion before releasing the slot; timeout, owner replacement or expired result lookup cannot authorize a competing publication. A request already dispatched may complete after stop; show pending until reconciled. Candidate scripts receive neither publisher credentials nor credentials that can forge accepted gate results. [ADR 0030](../adr/integration.md#adr-0030) records the evidence and open qualification.

A failed bundle remains unintegrated. Use bounded diagnosis/splitting with explicit new candidates and evidence; do not publish an untested subset or rerun unchanged hour-long suites indefinitely. Preserve dependency groups and prevent a blocked task from starving unrelated ready work. CPU observers expose backlog count/age, active bundle, gate duration and accepted throughput without model polling; bound queued worktrees/artifacts and slow task admission if integration cannot keep up. Reuse the existing integration-set/scan concepts and shared Runner/Keeper, not a new scheduler service. Independent CPU lifecycle, model cutoffs, scoped credentials and resource/budget limits remain in force. The [source inspection](research/bundled_integration_20261008.md) distinguishes reusable structures from legacy light/direct-push/manual-PR behavior that needs adaptation.

### Bounded manual Petri integration

The pre-MVP bridge uses authenticated owner/admin attestation through `POST /api/v1/projects/{project_id}/tasks/{task_id}/manual-integration`. It is separate from the ordinary worker workflow route. Its bounded request identifies one supported event, original expected revision, operation ID and structured evidence. Support only publication-required `freeze`, `accept` and `integration_progress` with an unknown publication outcome; reject caller-supplied guard facts, arbitrary exclusions and no-publication shortcuts.

The fixed server verifier checks the complete current task-token input binding, current satisfactory validation, unique frozen task IDs and heads, exact membership, target dev/main ref and base, candidate commit/tree, review and gate identities, passed default gate with confirmed cleanup, publication/inclusion evidence and the existing completion contract. Acceptance must match the original freeze's binding, validation snapshot, bundle membership, candidate, tree and base. Journal the complete validated envelope, canonical SHA-256 and `manual_owner_attestation` provenance atomically with the transition. Uncertain requests retain their original packet, operation ID and revision; unknown publication keeps integration ownership and cannot attest Done.

The bounded operator producer checks actual retained preparation/gate artifacts and Git/GitHub observations before preparing a private packet. Preparation and explicit submission are separate commands; neither prepares source, runs a gate nor merges a PR. These external observations are an owner statement. Server schema validation does not independently verify GitHub, and same-UID files do not establish an isolated trusted publisher. This scope introduces no receipt mount, signing key or filesystem-isolation claim. The automatic integration adapter remains unqualified. See the [manual integration runbook](implementation/manual_petri_integration.md) for acceptance and retry boundaries.

## 6. Minimal Cord communications

Start with a durable PostgreSQL mailbox and polling clients. A server-accepted message remains available across restart. There is no WebSocket, Git message bus, queue broker, email bridge or model-driven routing requirement in the bootstrap.

## 8. Controlled execution invariants

These are target design requirements for the later execution stage; the bootstrap implements no model-launch path. Task budgets use percentages of Claude's full weekly usage allowance, with a website-configurable approval exemption strictly below 1%. Shorter usage limits are checked separately. Larger tasks use time-limited approval windows, with aggregate daily build-usage caps per frontier model provider. Claude's default daily build cap is confirmed at 10% of its full weekly allowance. Eight hours is the configurable approval default. Multiple accounts per provider and switching near 98% account usage are confirmed. Each interval also has an overall usage cap. Other-provider caps, interval-cap defaults/model-pool mappings, closeout enforcement and explicit-stop policy remain open decisions. The configurable closeout-grace default is confirmed at five minutes. Expiry checkpointing, bounded closeout grace and the model-query cutoff are confirmed below. Contact-loss behavior is confirmed: selectable in the website, default finish-current-task.

1. Every managed launcher uses one deterministic admission contract, including Keeper, ensure, role respawners, fleet-watch, watchdog, cron/timers, manual wrappers and nested/resumed model attempts. Inventory and disable unadapted paths before controlled adoption.
2. Admission checks effective fleet/project/box/role/run controls, eligible work, compatible versions, claims, failure circuit, fresh usage, verified account/billing policy and owned resources. Reserve concurrency/budget/resources and action identity atomically. Repeated requests cannot create a second attempt.
3. Restrictive controls compose: central enable cannot clear a local disable; local enable cannot clear central pause or exhausted budget. Durable generations reject stale enables and stale permit redemption. Disablement survives restart, reinstall and ensure.
4. A short-lived permit is single-use and binds action, attempt, project, parent, actor, model/account, resources, generation and expiry. Keep reservations until completion or proven reconciliation. Expiry or lost contact does not prove a process stopped and cannot alone release capacity for duplicate work.
5. Database admission/redemption is not atomic with an OS process start. The implementation needs a durable local launch journal, process identity and replay reconciliation. A stop request immediately fences new admission; it is reported effective for a box only after that box reconciles in-flight starts and acknowledges the generation. During partition, show pending/unknown and follow bounded local expiry/checkpoint policy. Never claim an instantaneous universal physical stop.
6. Eligibility explanations use the same predicates as admission. Empty authorized queues, necessary reserves and provider waits are valid idle states. Do not start a model to decide whether work exists. No eligible integration means zero model launch.
7. Repeated unchanged failures back off and open a visible circuit. Time passing or a scheduler tick does not reset it. Recovery scripts have allowlisted actions, preconditions, idempotency, cooldown, attempt limits, verified postconditions and history; they cannot clear owner stops or authorize paid work.
8. Owner-confirmed contact-loss policy: finish the current authorized task by default. The control website offers checkpoint/stop at the next safe point as an alternative. Continuing the current task can include its previously authorized model calls/substeps; it does not authorize another task, broadened scope, an unbudgeted retry or a new independent attempt. Cache the selected policy/version and permitted task scope locally before execution. Explicit operator stop, normal drain, emergency termination and host shutdown remain distinct controls; contact loss alone does not impersonate an operator stop. Cached contact-loss behavior remains subject to the model-query expiry/cutoff and usage limits below; numeric offline bounds and enforcement still need qualification before execution.

Apply admission predicates to the requested effect: CPU execution needs its task/resource/runtime authority, inference additionally needs model/billing/usage authority, and publication additionally needs integration evidence and its scoped credential. A CPU-only attempt does not require an available model account. A zero-charge shared profile uses applicable slot/request/runtime accounting rather than native subscription quota; missing frontier usage metadata cannot block that profile by itself. Any frontier substep still needs its own valid allowance and billing controls. A model deadline is not a CPU deadline or an implicit merge deadline; record each relevant bound. Model-assisted diagnosis or correction requires current model authority even when its parent CPU gate remains authorized. No task phase inherits broader permissions merely because a previous phase was allowed.

Every SkyBuild-managed model process passes a separate work-need preflight before launch. The request binds one ready/in-progress task, exact current source head, committed input hashes, a substantive operation, named deliverables and measurable acceptance criteria; status checks, inbox polling and completion detection are not model work. The preflight does not grant execution/provider authority and must be composed with all admission, profile, billing, usage and approval checks. Before ledger cutover, the gate reads the three Markdown ledgers; after cutover it must read the API as sole task authority. REST/Cord calls themselves do not consume model tokens, but repeatedly returning unchanged responses to a model adds context and can consume tokens.

Worktree coordination, exclusive ports/endpoints, memory reserves, lanes and provider accounts are owned resources, not names guessed from directories. Reconcile declared reservations with observed reality; quarantine conflicts. Cleanup requires known ownership and retained failure evidence. Do not touch another session's stack or the application vault.

For offline completion, retain the task claim/fence and exposure as uncertain at the controller rather than reassigning on lease expiry alone. Keep a bounded local journal/spool of progress, results and effects; reconcile idempotently on reconnect before any next task. A completed local task is not assumed accepted centrally until its ownership/result is reconciled. A website policy change or stop for a disconnected box is pending until acknowledged. No exactly-once external-effect claim follows from this policy.

Fence local controls as well as central controls: a delayed local enable must not clear a newer local stop. Bind the relevant scoped control generations to the permit/journal; a single central generation alone is insufficient. Persist local restrictions before acknowledging them. After reboot or uncertain clock synchronization, do not extend an old authorization by restarting an elapsed timer; reconcile identity/deadline with the server or remain parked. Receipt ordering and wall-clock timestamps do not replace fencing.

Offline reservations are exclusive allocations to a verified worker/task/authority epoch, not copied cached balances. Sum them centrally before issuing more capacity. An offline worker cannot transfer unused allocation to another worker/account or carry it into an unreserved native/day window. Prepare any permitted cross-window allocation before disconnect; otherwise checkpoint at the binding boundary. Deadline accounting must include laptop suspend, or resume must park inference until deadlines can be reconciled. Wall-clock rollback, reboot or a restarted timer cannot extend authorization.

Track hosted quota, tokens, monetary cost and CPU/VM usage separately. Provider percentages are not interchangeable balances. ## 13. Compact component design

Optimize the amount of code and context that must be understood per change. Prefer short direct functions, shared value/validation helpers, data-driven command/adapter tables and one authoritative predicate over repetitive wrappers or elaborate class hierarchies. The owner accepts somewhat denser code to reduce token cost. Do not compress away transaction boundaries, authorization checks, units, ownership/fencing or failure handling; a tiny ambiguous state machine costs more to repair than it saves. Measure changed-code/context size alongside defects and correction cycles rather than chasing a raw line-count target.

Proposed logical modules, not a commitment to six physical files:

| Component | Owns | Compactness rule |
| --- | --- | --- |
| API | Authentication, project/operation scope, request/response validation, versioned routes and thin task/control pages. | One contract; handlers call domain/store functions, without duplicating policy. |
| Store | Transactions, revisions/idempotency, task/mailbox history; later control/run/resource records. | Explicit SQL/constraints and small transaction functions; one migration system. No generic workflow framework. |
| Client/CLI | API transport, typed results, bounded retry and concise views. | Python and shell share the client contract; skills wrap commands. |
| Runner/Keeper | Local launch journal, claims, execution/checkpoint/drain and adapter invocation. | Adapt existing code; task kinds replace permanent model roles where possible. |
| Observer | Independent process/resource/progress/artifact evidence. | One collector per box with adapters, shared cached state, no model loop. |
| Project/provider adapters | Product commands and policies; inference protocol/capabilities; cloud lifecycle. | Small explicit interfaces and configuration; reuse working pieces, avoid a plugin SDK until needed. |

Bootstrap topology is API plus PostgreSQL. The later central usage collector shares this service and Store; there is no additional usage microservice. Controlled execution later adds Keeper and an independent observer per worker box. Deterministic reconciliation can begin as one supervised bounded loop or timer with fenced ownership; adding API workers must not accidentally duplicate it. Cord is stored mailbox data in the same service. Add an outbox delivery loop only for external notifications that actually need one. No Kubernetes, Redis, separate message broker, per-role always-on agent, event-sourced rebuild of every table, or dynamic plugin marketplace is needed to obtain the initial product.

Keep first-class keys, revisions, statuses, ownership and foreign keys relational. Use JSON for bounded evolving metadata/artifact summaries where appropriate, without hiding required constraints inside arbitrary blobs. One append-only mutation/event vocabulary can serve history and diagnostics; not every heartbeat needs a durable audit event. Sample/coalesce routine observations, retain transitions/failures, and bound retention. Avoid replacing 27 legacy tables with a speculative universal table during the compatibility port.

Reuse a small effect record across adapters: stable operation ID, task/attempt, authority epoch/generation, input/policy digest, allocation references, dispatch state and external result reference. Commit intent before external I/O; do not hold a database transaction across a network call or pretend this creates a distributed transaction. Domain adapters supply dispatch/reconciliation rules. A lease identifies the reconciler; it does not erase an outstanding operation. Keep privileged publishing and trusted result acceptance outside candidate execution. This belongs in existing Store/Runner/adapters, not a generic workflow engine or new service. Qualify capabilities incrementally: CPU controls first, one bounded model profile next, then additional profiles/rotation/failover; unsupported providers remain disabled rather than blocking unrelated capabilities.

Extract code, not its accidental coupling. The existing endpoint helper imports SkyKeep provider/auth modules; a SkyBuild helper must depend on a small extracted neutral protocol/auth layer or its own minimal adapter, not the vault application's package. Application inference logic remains product code. Keep golden contract examples and meaningful concurrency/failure checks at boundaries rather than a test for every forwarding wrapper.

### Mechanical checks and independent adversarial review

The owner requires a separate model-session review for every code task before integration. The same model/provider may be used after qualification for that review class; a new session is not proof of model diversity or correctness. The author cannot approve its own patch. For MVP, review begins with existing applicable project checks and targeted test evidence. Known required-check failures return directly to rework before spending review tokens. The owner explicitly defers dedicated complexity/size checks, configurable gate enforcement and their GUI until the self-building MVP is running; retain their design without making their implementation, installation or reports an MVP gate. Expensive combined integration gates remain bundled; this does not introduce a full integration run per task.

The compact MVP reviewer uses adversarial perspectives on correctness, contracts, failure/retry/concurrency behavior, authority/data exposure, meaningful tests and unnecessary code. One bounded reviewer can cover applicable perspectives; no standing panel or per-perspective agent is required. Each finding gives its severity, exact revision and file/line/symbol or affected concept/contract, evidence or failure scenario, and a concrete correction or test with expected behavior. A conceptual finding must identify the affected boundary; vague demands to improve quality cannot block a task. Suggestions and style preferences are distinct from acceptance-blocking defects. Review may request fixes, simplification or targeted test additions without creating another work queue.

For the deferred post-MVP quality feature, the proposed Python profile uses Ruff's McCabe `C901` threshold of 10 and a function-size warning above 50 statements (`PLR0915`), drawn from documented tool defaults, not a universal Python standard. Explicitly enable selected stable rules and pin tool versions. Report function/module logical and source lines, additions/deletions and duplication alongside the metrics. Complexity violations newly introduced or worsened block; inherited debt is visible under a trusted scoped baseline rather than forcing unrelated rewrites. Size/growth triggers evidence-based review, not automatic deletion or a universal maximum file length. The owner/admin can configure thresholds, severity, applicable paths and narrowly justified exceptions in the GUI; each change creates a journaled policy version and invalidates affected readiness. Candidate code cannot weaken its own checks, baseline, prompt or suppressions. The proposed profile and compact prompt are in [review policy](review_policy.md), with primary-source evidence.

Owner direction for the first post-MVP work: include pinned Ruff checks, including McCabe, in the code-review path, scan the existing repository, and assign early cleanup tasks for all actual debt those checks expose. The baseline is a migration aid, not permission to leave findings unresolved indefinitely. Record each finding and close it with a behavior-preserving correction and applicable checks; false positives or necessary exceptions need an explicit owner-controlled disposition and review trigger. Keep the existing independent reviewer and trusted-gate boundary.

Additional whole-repository code review runs in the background whenever the first of two thresholds is reached after the last completed whole-repository review: 1,000 accepted commits or 5,000 changed source-code lines. Count accepted source changes once across development-branch boundaries, including additions and deletions; do not count documentation, generated files or the same merged change twice. Persist the review baseline, threshold crossing, reviewed revision, findings and completion so restart cannot lose the trigger. Permit at most one active whole-repository review. Keep the next trigger pending until every actual debt finding from the prior review has an accepted, published fix; only verified false positives or non-debt findings may close through explicit authorized disposition. A held trigger coalesces later commits and line changes without losing them. Fence ownership of each review run and deduplicate by durable review identity, baseline and source revision so accidental duplicate workers cannot publish a second finding set or create duplicate fix tasks. Unknown run outcome retains the hold until reconciled. CPU detection does not itself authorize a model call: qualified review, task budgets, subscription-only billing and cutoff still apply. The two numeric thresholds are owner-configurable in the GUI in a later settings slice. [ADR 0034](../adr/quality.md#adr-0034) records this cadence.

Rework stays on the same task and budgets. The author records a disposition and evidence for each finding; a separate reviewer verifies blocking findings against the revised inputs. Changed heads, definitions, relevant dependencies or active policies invalidate affected acceptance. Reviewer edits become authored work requiring another independent review. Findings and dispositions are append-only journal events; the UI exposes exact next action and unresolved criteria; dedicated metric comparisons and quality settings arrive after MVP. Bounded correction cycles park with a named blocker and owner question when disagreement or unchanged failure persists; rerunning until a reviewer says yes is not acceptance. Review cutoff, reservations and qualified-profile availability obey existing execution controls. If no reviewer is eligible, leave the task waiting for review; it cannot self-approve.

Compactness means removing unnecessary behavior, duplicate logic, speculative abstractions and redundant tests while preserving required contracts and failure handling. Do not reward minification, moving complexity into tiny wrappers, deleting useful tests, broad suppressions or hiding code in generated files. Necessary code growth can be accepted with a concrete reason. Reviewer success is fewer escaped defects and less correction/token cost through integration, not the number of objections or lines removed. [ADR 0033](../adr/quality.md#adr-0033) records the accepted direction and proposed mechanics.

Fall back to a supported LTS if compatibility or image provenance would otherwise delay the minimal service. Record image ID/digest, architecture and pinned runtime versions. A GPU serving container can use its vendor-supported CUDA/OS base independently; do not force it onto the control host's OS version. See [Ubuntu 26.04 release notes](https://documentation.ubuntu.com/release-notes/26.04/).

Separate resource shutdown authority from task completion reporting. Enforce a provider-side runtime/deadline where available plus a small bounded external reconciliation/backstop; neither depends solely on the rented box, a model session or the service being upgraded. A failed stop is a visible billing-risk state, not success. No observed queue activity or recovery retry can extend the owner's money/time limit automatically. At a hard deadline, checkpoint within the declared allowance and stop even if a task remains incomplete; preserve the recovery record rather than repeatedly extending rental. Keep owner-managed shared assets outside automatic power control.

Owner-requested advanced feature, deferred: cost-aware placement and checkpoint transfer of CPU work. For example, if a hypothetical $8/hour rented host with 32 cores and 64 GB RAM has only one remaining task while a suitable laptop has spare capacity, arrange portable subtasks/checkpoints so that task can move and the paid host can stop. These numbers describe the owner's example, not a selected/current rental. Anticipate this opportunity when splitting and assigning work, without making migration automation a bootstrap dependency. Laptop capacity, owner use and scheduled offline periods constrain placement; expose the recommendation and owner override in the control website.

Future policy should compare expected avoidable rental cost against transfer/setup time, expected rework and completion delay, using known data and explicit uncertainty. Verify destination resources, required architecture/OS/dependencies, input/artifact access and task capability; moving a task cannot silently substitute a required GPU/model profile or violate existing authority/billing/runtime budgets. Lower core count may change duration and should be part of the decision. Prefer cooperative application checkpoints or bounded resumable chunks; arbitrary process/RAM migration is not assumed. Preserve a versioned portable task/checkpoint contract now, while deferring scheduling, economics and transfer implementation.

A future transfer must durably copy and validate a checkpoint, reconcile/fence source execution and establish one destination owner before resume; a missing acknowledgment cannot create a second live attempt. Stop the rented host only after the destination/checkpoint is accepted, remaining host resources/tasks are accounted for and the authorized lifecycle permits shutdown. Owner-declared laptop unavailability can keep work on the rented host or defer it within explicit cost/runtime limits; it cannot grant unlimited rental. Existing hard provider/runtime backstops still apply when transfer fails. Use CPU observations for placement/status, not a continuously watching model. API task `SKYBUILD-COST-AWARE-JOB-TRANSFER` and [ADR 0020](../adr/hosting-recovery.md#adr-0020) retain this direction.

Owner-requested advanced feature, deferred: recurring/transient capacity calendars and deadline-driven batch bursts. A shared laptop can be reserved for household use on Thursdays and available on other days, subject to observed health/resources and one-off exceptions. Store timezone-aware availability, owner reservations/offline periods and overrides separately from actual reachability/capacity. Forecast task duration and checkpoint needs against those windows; drain or transfer work before a reservation rather than assume an occasionally available laptop is always on. The household schedule is an example requirement, not machine enrollment or a live configuration change.

Let the owner choose a desired completion time and compare local/transient execution with a bounded cloud burst. A control-panel decision should show the selected workload, dependency-ready CPU work, expected local/burst finish times and uncertainty, suitable resources, startup/staging/drain time and estimated total rental cost with a hard money/runtime limit. Core integration already uses task bundles under section 2; this later feature places ready integration/validation work on optional burst capacity. Account for serialized merge ownership, dependency order, memory/test lanes and external endpoint contention; many tasks do not imply useful parallel speedup. Work waiting on model output is distinct from ready CPU backlog. Do not start a paid CPU host merely to wait for unavailable inference. Batch staging must not conceal the deadline cost of delaying critical-path work.

Provision under explicit existing spend/runtime authority for a pinned selected workload, stage its inputs and fill usable capacity within resource limits. New backlog cannot silently enlarge the batch or extend rental. When the workload is complete, drain, preserve/attach results or portable tail checkpoints, verify no other owned work remains and confirm provider stop through the qualified adapter, backed by an independent hard shutdown limit. Model queries retain their separate approval/billing/cutoff policy; CPU tasks report results without model watching, and completed CPU work need not wait for later model review before the burst ends. Keep the laptop API/PostgreSQL authority separate from the burst worker. An hour-or-two burst or a 32-minute busy run is the owner's example, not a promised billable duration. Reuse existing Store/Observer/Runner/provider-adapter contracts with a small deterministic planner; no new cluster framework or always-on reasoning service is proposed. API task `SKYBUILD-BURST-CAPACITY-PLANNING` and [ADR 0021](../adr/hosting-recovery.md#adr-0021) retain this direction.

The advanced compute backend is deliberately unselected. Allow a configured set/pool of boxes and investigate suitable managed batch/serverless runners behind the same portable task/result/checkpoint contract; do not assume request-oriented serverless functions fit build/integration workloads or cost less. The owner requested a later research-and-test spike before choosing this architecture. API task `SKYBUILD-COMPUTE-ECONOMICS-SPIKE` compares existing machines, VM bursts and qualified serverless/batch candidates with representative fixed CPU-ready workloads. Verify current official pricing, runtime/resources, Git/artifact access, queue/startup/cancellation and durable-state constraints at that time. Run a bounded isolated test under a separately selected monetary/runtime cap, measuring total cost per accepted workload and time to completion, including startup, staging, idle time, transfer/storage, retries and stop confirmation. Preserve estimates versus observed charges and uncertainty. Produce reproducible evidence and a recommendation, not a presumed financial saving. No test, cloud spend or deployment is authorized by recording the spike; initial laptop hosting and core extraction do not depend on it.

## 16. SkyBuild building itself

The owner-confirmed MVP milestone is a running SkyBuild that can rebuild itself and add features using parallel workers. Demonstrate at least two independent tasks active in isolated owned worktrees under shared resource/budget controls, with durable next-action status, separate review, bundled tests/publication and recoverable failure/handoff. More than one active worker does not require simultaneous model calls when a qualified profile has only one available slot. Keep the stable controller serving task/status operations during candidate work. A successful feature change must reach the accepted candidate and controlled update path; it cannot promote itself or require a complete controller rewrite.

This milestone composes the minimal task/Cord authority, applicable control slice, one qualified author/reviewer profile, Keeper workers and bundled integration. It does not wait for the dedicated complexity/size gate suite or GUI, all provider/account variants, full legacy migration/extraction, advanced cloud scheduling or HA. Existing applicable checks and independent code review remain. Use SKYBUILD-SELF-BUILD-MVP as acceptance work, not a new runtime subsystem.

The file-ledger bootstrap is complete for SkyBuild; use the accepted task/mailbox API for current work. Keep the last accepted SkyBuild controller/version outside candidate worktrees while SkyBuild builds its next version. A task cannot change its own stop/budget authority or grant its replacement broader permissions. Building and testing a candidate does not deploy it. The owner/manual recovery command remains usable without the new API or a model.

Validate candidates against disposable PostgreSQL, a fake clock/provider and controlled process adapters before a canary. Use backward-compatible expand/migrate/contract schema changes where needed. A service binary rollback after database writes is allowed only when that binary is compatible with the current schema/history; otherwise recover forward or use an explicit restored/reconciled boundary. Do not let an automated “rollback” reopen old SQLite or erase completed task/message history.

During a controller update, drain new admissions, preserve local stops and in-flight reservations, install a pinned artifact, verify protocol/schema/health and keep workers parked until reconciliation. The independent observer and cloud deadline backstop should survive a controller/worker update. Start with one active controller; an external recoverer may restart only the approved non-model service artifact, without enabling tasks. No automatic candidate promotion by its own successful self-report. Owner-requested second-laptop HA/DR hot failover is very low priority after core work, tracked by API task `SKYBUILD-LAPTOP-HA-DR`. It is not a bootstrap requirement. Preserve configuration portability now, but do not build replication/election machinery early. Later failover must provide one fenced active controller and reconcile in-flight work; stale-heartbeat promotion cannot create a second writer. HA does not replace the planned daily dump commits or the separate low-priority restore/journal-rebuild validation.

Record self-build tasks as ordinary SkyBuild project work with exact input/candidate/deployed revisions, result artifacts and provenance. Reuse the same compact context, deterministic checks and bounded inference routing intended for SkyKeep. This makes inefficiency measurable without running an unlimited self-improvement role. Optimize for accepted changes per premium token and useful CPU throughput, not number of agents, commits or occupied machines.

## 17. Failure-driven architecture revisions

| Failure path examined | Prevention or explicit limit carried into the design |
| --- | --- |
| File/API both accept task edits | Frozen import and one recorded authority switch; exports become read-only. |
| Legacy import overwrites bootstrap rows/sequence/schema version | Staging/provenance and project/legacy ID mapping; refuse conflicts before runtime activation. |
| Two launchers both observe one free slot | Atomic reservation rechecks; the deliberately weakened admission model exhibits oversubscription. |
| Stop/local disable arrives after permit reservation | Revalidate controls/generation at redemption; pending physical-stop acknowledgment and durable local journal remain separate. |
| Lost launch/inference/cloud-create response followed by retry | Stable operation identity, held exposure and explicit reconciliation; no automatic duplicate/fallback. |
| More drafts/test lanes saturate brodson or evict its model | Separate reported 4/2/1 pools, cross-project/test reservations, bounded requests/queues and integration priority; qualify shared hardware and external demand, then reduce drafting when validation backs up. |
| Cheap model produces many plausible bad patches | Qualified task classes, deterministic checks, sampled/risk-based review, correction caps and quality circuit. |
| GPU rented while work waits on decisions or validation | Only ready backlog counts; separate CPU/endpoint dependencies and measured break-even. |
| “Start aragog” interrupts running work or boots old fleet | Read current provider/work state, refuse implicit restart, boot disabled/report-only and explicitly drain before changing runtime limit. |
| Stop says success but cloud resource keeps billing | Verify provider lifecycle, track unknown/stopping state, deadline backstop and residual-storage inventory. |
| Empty queue stops the task/mailbox authority | Control server uses durable-host lifecycle; idle shutdown applies to burst workers/inference. |
| Builder deploys a broken version of itself | Stable controller plus disposable validation, pinned manual/canary promotion and independent recovery/stop path. |
| Compact abstraction hides safety or creates token-heavy debugging | Keep ownership/transaction boundaries explicit; measure context/correction cost, avoid speculative frameworks. |
| Two dependency edits each look acyclic and jointly form a cycle | Serialize project dependency mutation or use validated serializable retries; commit validation/history atomically. |
| Delayed local enable or reboot extends stale authorization | Persist scoped local generations, reject stale commands and reconcile deadlines before any new work. |
| Cheaper model silently changes a product gate's semantics | Separate coding-vs-test profiles, record actual model/config and invalidate incompatible evidence. |
| Inference health probe evicts a model or bypasses the rental window | Prefer metadata checks; genuine generation probes share admission and endpoint budget. |
| Client spoofs message sender or changes its own execution scope | Derive actor from credentials; use a small explicit project/operation/recipient scope matrix, with owner-managed revocation. |
| Many nominally cheap tasks or hidden retries exhaust Claude allowance | Whole-task estimates, parent/child accounting and atomic account/window reservations; no cap reset by splitting, retry or resume. Unknown estimates do not qualify as below threshold. |
| Every component independently polls usage or a cache read generates a paid prompt | One fenced collector, passive metadata/bounded adapter queries and cache-only REST reads; unknown billing/support stays explicit. |
| Model views duplicate a shared pool, or an expiry hint sends work to an incapable model | Preserve native pool identity and parent caps; expiry priority applies only after capability/quality/budget eligibility. |
| Account switch resets build budgets or two credentials duplicate one allowance | Bind actual account/pool identity, retain approval baselines and shared usage, and atomically reserve across account/model and parent limits. |
| Workers overwrite a shared CLI login or race credential refresh | Isolated per-account profiles, immutable attempt binding and one supported refresh owner; no secrets in ordinary REST/task/log data. |
| Old coordinator auto-resumes after switching to another engine | Fence and stop/reconcile it before handoff; durable checkpoints and operation identities prevent duplicate continuation. |
| A percentage read is mistaken for a budget reservation | Atomic admission includes interval/daily/native/task exposure; concurrent readers cannot each spend the same headroom. |
| Approval renewal, midnight or another worker creates a fresh daily allowance | Aggregate provider/day accounting across projects and workers; preserve usage and uncertain exposure across window renewal and day rollover. |
| A bundle's named “strongest” profile omits another member's tests | Union of required checks; only proven policy dominance permits deduplication. |
| Target changes after local checks; an old integrator still publishes | Trusted publisher, durable unresolved intent and remote enforcement of the tested head/base; a lease alone is insufficient. |
| Candidate scripts forge success or change their own required checks | Accepted policy snapshot and trusted result origin; publication/check credentials outside candidate execution. |
| Parent/child or bundle accounting duplicates or loses model usage | Reservation subdivisions, atomic settlement and single provider charge with explicit task allocation. |
| Laptop suspend or window rollover extends offline spending | Suspend-aware deadline or parked resume; exclusive allocations for each applicable accounting window. |
| Restoring an older database revives matching permits or credentials | New authority epoch, quarantined restored authority and reconciliation of existing effects before resumption. |
| Code-complete task remains silently unmergeable | Explicit state machine, append-only task journal, next-action owner and durable reassessment; control page exposes blockers and stalled transitions. |

The successive reviews were A1 (document authority, bootstrap and complete extraction), A2 (compact components, capability routing, host lifecycle and self-build), and A3 (import collisions, dependency write skew, local control replay, idempotency retention and test-model integrity). They are refinements within this one active draft, not three competing architecture documents. See [reuse and capability evidence](research/reuse_and_capabilities_20261008.md) for inspected source anchors and tool limitations.

The A30 audit adds effect-boundary, gate-union, allocation and recovery-epoch refinements in [ADR 0030](../adr/integration.md#adr-0030), with a sampled [publication model](models/Publication.md). These reviews refine proposals; they do not establish live fixes. The [design model notes](models/README.md) state the actual checker coverage and limitations. Remaining policy questions now include endpoint qualification/capacity, rental budget/deadline/idle margin, concrete Tailscale exposure/access-rule qualification, offline budget/deadline enforcement, any future server provider/image choice and external stop-backstop ownership. Initial laptop hosting is settled by ADR 0006; a later move requires an owner tradeoff discussion. Carry these into the implementation plan only to the detail needed for the selected next area.
