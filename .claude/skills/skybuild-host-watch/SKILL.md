# SkyBuild host watch

Use `scripts/host_watch.py` from the exact checkout on each participating SkyBuild box. One `--watch` process samples memory and disk headroom, task-owned disposable Docker containers and prunable Git worktree records every 60 seconds, then atomically replaces a JSON state file. It makes no network or model calls. Its lock refuses a second watcher for the same file, and its maximum lifetime defaults to eight hours.

Use a writable scratch path outside the checkout, such as `/home/kevin/my_code/skybuild-gate-tmp/host-watch.json`, with `--reserve-gib 8 --disk-reserve-gib 4` on the owner's current host. Start one watcher for sustained work, then read the state file only before a resource-heavy command or when diagnosing pressure. Treat `low`, `unknown`, `stopped`, or a sample older than two intervals as a reason to defer new heavy work. `attention` reports owned Docker containers older than the gate deadline or prunable worktrees for manual reconciliation. Allow room above the 8 GiB memory reserve for the command's own demand; the disposable PostgreSQL gate accepts `--min-available-gib 10` for this session.

Commit and propagate the script and skill with SkyBuild before relying on them on another box. Verify each box's checkout head and run the local copy there; each Codex session must read this skill itself. The watch reports pressure and ownership hints; it does not stop processes, remove containers or worktrees, or guarantee future free memory. Never use broad process-kill commands to manage it. To stop a watcher, create a file named `<state path>.stop`, then wait for the state to become `stopped` within one interval; the watcher removes that request file. A managed session handle is also suitable. The PID in the state may be namespace-relative. Leave unrelated sessions and containers alone.


When worker units exist, pass `--jobs-registry <launcher state directory> --capacity-state <scratch>/capacity.json --new-job-limit-gib <launcher MemoryMax GiB>` to the same watcher. The launcher owns one JSON manifest per attempt; the watcher reads at most 64 manifests and cgroup v2 `memory.current`, `memory.peak`, and finite `memory.max`. It retains completed peaks and source times in `capacity.json` across watcher restarts. Read `max_new_jobs` only when the capacity sample is fresh and its status is `ok` or `needs_completed_measurement`; the latter permits only one pilot job. A launch intent, missing cgroup, stale peak, or a measured peak above the configured new-job cap blocks progression. The target increases by at most one after five healthy minute samples and observation of the prior concurrency level; it is advisory, never a launch permit. The launch manager must enforce the same hard cap and `Nice=10`, plus its independent authority and ownership checks. Keep finished unit evidence until its peak is sampled.
