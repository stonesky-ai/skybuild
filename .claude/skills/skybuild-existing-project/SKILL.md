# Adopt an existing project

Use this occasional onboarding methodology for projects such as SkyKeep.
Invoke with `/skybuild-existing-project`, `$skybuild-existing-project`, “onboard an existing project”, or “plan legacy backlog migration”.

Preserve → map → interview → disposition → release.

Read [migration method](references/migration-method.md) when preparing a plan or pilot. It defines the dependency review, HIL questions and editable decision packet.

- Start with planning and read-only discovery. Invoking this skill does not authorize import, enrollment, task mutation, worker dispatch or retirement.
- Preserve source identity, original history and prior classifications. Hold means classification awaits reconciliation; it does not mean the original work is incomplete.
- Treat every record as ordinary task history with explicit provenance and evidence coverage. Do not exclude legacy records from common journal and consistency checks. Identify tool coverage gaps rather than claiming missing checks ran.
- Map prerequisites separately from milestone membership. An obsolete milestone makes related work a retirement candidate; it does not prove every task is obsolete.
- Resolve intent through human-in-the-loop (HIL) questions for connected groups. Retain useful shared tasks and propose new milestone links explicitly.
- Prefer a linked, ordinary reconciliation task with a bounded evidence-review mandate. Keep the original held until an authorized disposition. Direct release of an original is an alternative only when its mandate cannot be mistaken for rebuilding old work.
- Release small, sufficiently defined batches through the qualified workflow. Ready is a defined next action, not permission to execute or a claim that the historical work needs implementation.

Return an editable migration plan, graph proposals with evidence, grouped HIL questions, proposed task dispositions and a bounded pilot. Separate confirmed facts, inferred relationships, human decisions and unresolved questions. Name unsupported runtime operations as blockers. Save no credentials in the packet.

For SkyKeep, keep its product data and task authority separate from SkyBuild until an explicit cutover is approved. This skill does not authorize that cutover or reuse SkyBuild's own migration receipt.
