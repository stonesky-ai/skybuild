THE TOOL PROPOSED BY THIS HANDOFF

Dependency path first. Schedule claims only with data.

01

Dependency path

Walk declared prerequisites backward from one target. This is deterministic for a fixed, validated task snapshot.

02

Blocked and ready view

Classify unfinished prerequisites using task state and acceptance evidence. A status label alone does not prove completion.

03

Schedule critical path

Keep this separate. It needs duration estimates and scheduling assumptions; shared people and worker limits add resource constraints.

Deterministic core

  • Read one frozen snapshot and identify its commit or API version.
  • Validate IDs, project boundaries, missing references, self-edges, and cycles.
  • Return only the target's transitive prerequisite graph; keep parallel branches visible.
  • Sort topological layers deterministically without inventing edges.
  • Show blockers, next actions, missing evidence, unknowns, and data-quality errors.
  • Emit machine-readable JSON and a concise human report with task IDs and direct edges.

Source-of-truth boundary

Before cutover, analyze a frozen Git-backed ledger snapshot. After cutover, use the versioned read-only task API or export. Do not blend authorities or snapshots.

Milestones point to an accepted task or an explicit owner-recorded event. The MVP target is the task SKYBUILD-SELF-BUILD-MVP, not a guessed title match.

BOUNDS FOR A FIRST SLICE

Keep analysis read-only and verifiable

In scope

One project, one frozen task snapshot, one target, dependency validation, deterministic paths and layers, incomplete blockers, and a concise report with a JSON form.

Not in the first slice

No automatic task creation or edge edits, model-based dependency authority, live ledger migration, schedule optimizer, workforce planner, GUI, notifications, launches, integration, or deployment.

Optional model skill

Only after the CLI contract settles. A model can summarize tool output and cite IDs and edges; it cannot mutate tasks, dependencies, authority, budgets, or execution state.

Open decisions for task selection
  1. Is this a planning task or implementation of an already selected task? Assign a stable ID if it is new.
  2. Which input contract matches the current authority phase: frozen ledger, canonical export, or read-only API?
  3. What evidence means “accepted” for generic tasks, including work that does not need review or merge?
  4. Is the first release dependency-only, or is there real duration and resource data for schedule estimates?
  5. Where should the CLI and output live? Is the model skill a later task?
  6. Which consumers need the first output: CLI, future UI/API, or both?
